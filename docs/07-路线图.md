**范围**：

- 进程管理：运行登记、2 秒状态轮询、`taskkill /T` 停止、重启、退出确认
- 内置静态服务器（embedded 型）+ 日志回读端口
- profiles.json：覆盖锁定 / 保存 / 原子写
- 打包：build_windows.bat 单 exe

**验收**：docs/01 §5 全部 6 条（核心是 docs/02 附录 A 符合率 ≥ 90%）。

## v0.4.7 · 运行感知与多 nginx 配置（2026-09-30 需求轮，已实现）

**范围**：

- **外部运行感知**（docs/03 §3.6 + docs/04 §2）：列表状态点新增**蓝 ○ = 外部运行**——端口在监听但不是精灵启动的（自己在终端/IDE 起的服务、nginx/docker 正在服务的站点）。判定链（`portman.listen_map` 一次连接表快照 + `proc_paths`/`under_dir`）：监听进程 cwd/exe 落在某项目目录内 → 最深项目**确证**命中；进程路径读不到 → 按端口**推断**（卡片措辞标明）；路径可读但不属于任何项目 → 只是端口被占、不算。工具栏计数显示 `运行中: N（外部 M）`；点「启动」照常走冲突预检。**为什么不能光按端口**：本工作区 21 个 Vite 项目共用默认 5173，纯端口匹配会把全部项目误点亮（2026-09-30 实测 18 个误报 → 收紧后仅剩真正在跑的那 1 个）
- **「📶 端口总览」**（docs/04 §4.8）：工具栏按钮，本机全部监听端口 × 项目归属一屏（端口/监听地址/进程/PID/归属项目/启动项/是否精灵管理），归属判定 管理中运行项 ＞ 启动项端口 ＞ 端口知识库；默认 2 秒自动刷新，后台线程拉取
- **nginx.conf 手动指定可多个**（docs/02 §9.1）：设置里单行输入框 → 多行文本（每行一个，浏览可多选），`ngxscan.manual_split` 纯函数解析（兼容引号/目录行、去重保序）；有效份全部解析，部分无效忽略并列进扫描日志，全部无效仍不回落自动探测
- **外部项目「结束进程」**（确证命中限定，docs/04 §3 + docs/08 §10.3）：蓝 ○ 且确证归属的启动项，卡片按钮与右键菜单给**「结束进程」**——与精灵「停止」区分：弹确认框（进程名/PID/未保存数据提醒）→ `stop_tree` 树杀监听 pid → 杀后复核端口释放、写运行日志。推断命中与 nginx 合成站点**不给**结束（按端口乱杀可能误伤无关进程/docker）；「全部停止」只停精灵受管项目，不批量结束外部进程
- selftest 新增：`under_dir` 路径判定 + listen_map 真实回环套接字快照（发现/pid/同口径/关闭后消失）+ manual_split 多路径不变量 + stop_tree 结束真实子进程

**验收**：selftest 34/34 + 全部不变量（含端口）通过；冒烟：84 项目扫描后外部运行判定仅命中真实在跑的 `G_BlockWorldLike`（node.exe cwd 在项目内、监听 5173），端口总览 33 行与汇总正确，设置多行框回显正常；外部结束端到端（临时目录造项目、起真实 http.server：确证命中 pid 一致 → 卡片出现「结束进程」→ 确认后进程退出、端口释放、状态回落 stopped）。

## v0.4.9 · nginx 配置排除机制（2026-10-01 需求轮，已实现）

**范围**：

- **profiles `settings.nginx_excluded`**（docs/02 §9.6/docs/05）：多行文本每行一个（与 `nginx_conf` 同风格，容忍引号/空白行、去重保序），不校验存在性

- **设置 UI**（docs/04 §4.3）：nginx 区新增"排除的 nginx 配置"多行框 + 「勾选要排除的配置…」弹窗（列出探测候选 + 当前已填项，勾选 = 排除；候选口径与 apply 一致，手动指定模式下只列手动那几份）
- selftest 新增 `check_nginx_excluded`：normcase 匹配/保序/边界/去重不变量；apply 级端到端四场景冒烟（真实两份配置：排除 F/全排除/不排除/指定+排除）
- **顺修两处 v0.4.7 回归**（端到端冒烟发现）：① apply 头部被改成无条件 `manual_split(manual)`，手动框留空时自动探测整条丢失（nginx 关联恒为空——此前"缓存里 nginx 全空"疑团即此所致），现恢复"留空 = 自动探测、非空 = 只认清单"；② "部分手动路径无效"提示被 `lines` 重置吞掉、正常路径永不显示，现与排除注记一并置于各配置行之后

**验收**：selftest 34/34 + 全部不变量（含 nginx 排除）通过；apply 端到端（真实机器）：排除 F 盘 → 只解析 D 盘且日志注明、全排除 → "已全部排除"提示、不排除 → 2 份全解析、手动指定+排除同路径 → 排除赢。

## v0.4.18 · 防火墙写入真机修复（2026-10-02 bugfix，已实现）

**背景与症状**：用户首用「写入 / 更新规则」报「未完成：未获得管理员授权（UAC 被取消）…」，且 Windows 全程**没有弹出 UAC 提示**。真机诊断（Python 3.14 / Win10 19044）揪出两层叠加根因——v0.4.6 上线以来防火墙写入**从未真正成功过**（selftest 只测纯函数，netsh/UAC 全链路一直躺在"下一步"清单里）。

**根因 ① description 含 `|` 被 netsh 拒绝**：`rule_desc` 格式 `标记|身份键`，netsh add rule 实测报「描述包含无效的字符，或具有无效的长度」——规则根本建不成。分隔符改 `;`（实测 `; , -` 均被接受；身份键来自 Windows 目录名、天然不含 `;`，`project_from_desc` 精确往返不受影响，且从未有存量规则落盘，零迁移）。

**根因 ② 提权回读 Permission denied 被误报成"UAC 被取消"**：Python 3.12+ `tempfile.mkdtemp` 在 Windows 给临时目录设受限 ACL（SYSTEM / Administrators / **OWNER RIGHTS**，无用户 ACE）；UAC 提权进程**新建**的结果文件所有者落到 Administrators，精灵进程（非提权令牌内 Administrators 为 deny-only、又非所有者）读回必被拒（Errno 13）。修复：`apply_ops` **预创建空结果文件**——文件所有者留在精灵一侧，提权脚本只覆盖写，任何 ACL 环境都读得回。回读仍失败的兜底消息也从「未获得管理员授权」改为「命令已发送，但无法回读执行结果，请刷新规则列表核实实际状态」（不再误导）。

**UAC 不弹窗不是 bug**：这台机器 `ConsentPromptBehaviorAdmin=5`（Win10+ 默认，仅对非 Windows 程序提示），微软签名的 powershell 经 `-Verb RunAs` **静默自动提升**，AppInfo 服务正常即无声完成；提示级别为「始终通知」的机器才会弹窗点「是」。fwman 模块头已记录此行为。

**顺带**：`netsh profile=any` 的规则 COM 读回 Profile 位掩码 = 0，`profile_label` 原样显示裸 "0"，现归入「全部」（修复前规则从未写入成功，读侧从未见过真实数据）。

**验收**：真机端到端——`apply_ops(op_add)` 返回 ok=True，`list_rules` 读回规则（desc=`项目启动精灵管理;…`，端口/协议/范围正确）→ remove 清理 → 复核消失，全程无 UAC 弹窗（Consent=5 静默提升）；selftest 34/34 + 全部不变量通过（`check_fw` 补 desc 不含 netsh 拒绝字符 + 分隔符往返断言；JSON 解析补 Profile=0 →「全部」）。

- **core/launcher 注入链**（纯函数 + 一处 I/O）：`npm_run_script`（识别 `npm[.exe/.cmd] run <script>` 形态，含绝对路径/带尾参）/ `script_uses_vite`（`(^|\s)vite(\s|$)` 词边界，vitest、my-vite 不误命中）/ `inject_lan_host`（尾部追加 `-- --host`，已带 --host 判重、不改原列表）/ `pkg_lan_info`（读 package.json → scripts + vite 依赖）/ `entry_lan_gap`（vite 依赖 + 目标 script 以 vite 为入口**双条件**；cwd 子目录 package.json 优先，无文件回落项目根）/ `maybe_lan_host`（开关门控）。`launch` 加 `lan_auto_host` 参数，**注入在 `_resolve_exe` 之前**——解析后 npm.cmd 被包成 `cmd /c …` 就认不出 npm run 形态；`entry.command` 本身不被改动。只认 npm 家族，nodemon 等其他 dev 工具的 --host 语义不同、不碰
- **防火墙开通提示**（`FirewallDialog._maybe_lan_hint`）：写入规则成功后，若总开关未开且项目存在"Vite dev 且未带 --host"的生效启动项（过 `profiles.effective`，locked 覆盖也纳入），askyesno 提示开启（文案说明下次启动生效、运行中服务需停止再启动）；选是 → settings 落盘
- GUI：启动调用点传 `settings.lan_auto_host`；EmpLike 此前手工写的 locked entry（带 `-- --host`）与此开关并存，判重不重复注入
- selftest 新增 `check_lan_host`（形态解析 / vite 词边界 / 注入判重 / 双条件 + cwd 回落 / 开关门控）；界面词条 3 条进 zh-CN 词典（check_i18n 强制）

**验收**：selftest 全过（含新段）；DungeonDemo 真机端到端——开开关后注入命令 `npm.cmd run dev -- --host` 实测：5173 空闲时起在 5173 且监听 `0.0.0.0/[::]`，`curl http://192.168.232.129:5173/` → **HTTP 200**（EmpLike 同链路当日已验证）。

## v0.4.21 · 便携环境路径（2026-10-02 需求轮，已实现）

**背景**：精灵的卖点是"拷走即用"，但项目依赖的工具不在精灵身上——把工作区连同精灵拷到另一台电脑，机器上没装 Node/Java/Maven 时项目起不来（v0.4.12 的 nvm 回退只救本机装法）。用户计划用 Tool_PortableEnvironment 做便携环境包（尚未完成），要求精灵先支持**可配置的环境依赖路径**：随行带了便携环境就能启动，如便携 Node 起 G_EmpiresLike。

**范围**：

- **settings.portable_env**（多行文本，默认空，零迁移）：每行一个目录，容忍引号/空白、去重保序、**不校验存在性**（未插的 U 盘也可保留）；原样存储（含 `%VAR%`/相对路径），解析时才展开——**相对路径锚精灵所在目录**（paths.app_dir()，便携铁律），精灵连同 `portable\node` 一起拷走配置不用改
- **core/launcher 解析链**（解析纯函数 + 轻 I/O）：`portable_dirs`（文本 → 规范化目录列表；expandvars/expanduser；相对锚 base_dir；normcase 去重保序）/ `portable_search_dirs`（根 → 查找目录 = 根本身 + 一级子目录 + 各子目录 `bin`——便携 node 目录直接含 node.exe、整包目录 node/ jdk-17/ 并排、JDK 根目录 bin\java.exe 三种布局都命中）/ `java_home_from`（检出含 bin\java.exe 的根/一级子目录 → JAVA_HOME，gradlew/mvn 需要）/ `portable_path_env`（子进程 PATH 前置便携目录——npm run 派生的 node/vite、脚本裸调 java 靠 PATH 找，整条启动链都要看得见）/ `_in_dirs`（目录内存在性判定，无扩展名首词按 PATHEXT 补试）
- **解析顺序**：`which_first(cmd, extra_dirs)` 便携目录 → PATH → node 家族回退（v0.4.12 链路保持在后）；extra_dirs 非空时绕过 `_which_cache`（不同配置结果不同，存在性判定廉价；"未命中不缓存"约定不受影响）。`preflight`/`_resolve_exe`/`launch` 加 `portable` 参数（传配置根，内部展开）——**预检与启动同一口径**，便携环境能启动就不会被预检拦下；`_resolve_exe` 的 .exe/.py 等非本地首词也补走 which（此前落空原样交给 CreateProcess）
- **GUI**：设置对话框「局域网访问」后新「便携环境」区块——多行文本框 + 「添加目录…」（askdirectory 追加判重）+ 灰字说明（先于 PATH/子目录与 bin 也搜/相对锚精灵目录/留空只用系统 PATH）；`_save` 去重保序写回；main_window `_portable_roots()` 统一给 preflight/launch 传参
- **边界**：全局粒度不分项目（与 lan_auto_host 同思路）；便携目录只影响依赖解析与子进程环境，不改 entry.command；static/embedded 启动项不经过此链路
- selftest 新增 `check_portable`（文本解析/三布局展开/extra_dirs 先于 PATH 且绕缓存/PATHEXT 补试/JAVA_HOME 检出/env 前置保原值/preflight 同口径）；界面词条 4 条进 zh-CN 词典（check_i18n 强制）

**验收**：selftest 34/34 + 全部不变量（含新段）通过；沙盒端到端冒烟真起子进程——相对路径锚 SPIRIT_HOME、preflight 放行、首词解析到便携绝对路径（`cmd /c <便携>\tools\envprobe.cmd`）、子进程内 `where node.exe` **首个命中便携 node**（排在本机真 node 之前）、`JAVA_HOME` 指向便携 JDK、设置对话框保存回读正常。

## v0.4.22 · 便携环境展开加深，对齐 Tool_PortableEnvironment（2026-10-03 适配轮，已实现）

**背景**：Tool_PortableEnvironment 交出第一版便携环境（`env.bat` 注入 PATH + `start_spirit.bat` 启精灵，runtime\ 下 node/python 槽位 + java 预留槽）。对照发现两机制内核一致（便携优先/PATH 前置/JAVA_HOME 检出），但**展开深度差两层**：`env.bat` 通配 `runtime\java\<任意名>\bin`，而精灵 v0.4.21 的 `portable_search_dirs` 只展开一级子目录——实测：配置 `...\runtime` 能命中 Node/Python，配置整包根全不命中，JDK 槽位（二级 `java\<名>` + 三级 `bin`）永远够不到。适配方向定在精灵侧（消费方容忍生产方布局；env 包的 JDK 任意名解压设计不该迁就）。

**范围**：

- `portable_search_dirs` 展开从"根 + 一级 + bin"加深为"根本身 + 各级子目录**至三级** + 各级子目录 `bin`"——整包根直填（`runtime\node` 二级、`runtime\java\<任意名>\bin` 三级）与 env.bat 通配行为对齐；**bin 与点目录不再深入**（工具不住那里，也防误配大目录扫爆）；目录读不到按空子目录处理
- `java_home_from` 改为复用 `portable_search_dirs` 同一展开（找 `bin\java.exe` 所在目录）——单层/深层 JDK 布局同一套逻辑，签名不变
- 设置对话框灰字说明更新（"嵌套子目录与其 bin 也会搜索，整包根目录可直接填入"，zh-CN 词条同步，check_i18n 强制）
- selftest `check_portable` 补 2b 段：整包根直填三布局命中 / bin·点目录不深入 / `which_first` 命中便携 npm / 深层 JDK 检出

**验收**：selftest 34/34 + 全部不变量通过；真实 Tool_PortableEnvironment 目录实测——配置整包根与配置 `runtime` 等效，node/npm/python 全部命中便携版（此前整包根全落系统版）；`JAVA_HOME` 槽位暂空如实未检出（放入 JDK 后同链路自动命中）。

**已知边界**：便携根应是环境目录——把很大的目录（如整个工作区）填进来会逐层展开、PATH 前置也随之变长（线性代价，能跑但没意义）；展开不跟随符号链接循环（listdir 幂等，bin/点目录已剪枝）。
