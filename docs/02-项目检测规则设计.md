# 02 · 项目检测规则设计

> 本文档是项目启动精灵的核心设计：如何从"一个目录"推断出"它该怎么启动"。所有规则均以 2026-09-21 对工作区 28 个真实项目的盘点为校准基准（附录 A 是全量预期表，也是 v0 实现后的验收对照表）。

## 1. 核心概念

### 1.1 检测的单位是"目录"，不是"项目"

规则按**目录**评估。一个项目 = 项目根目录 + 少量约定子目录（见 §2 扫描范围）。每个目录最多命中一条主规则；项目的启动项集合 = 根目录命中 + 各约定子目录命中的并集。

### 1.2 启动项（Launch Entry）

一个启动项是列表和界面上可"双击启动"的最小单位：

| 字段 | 说明 |
|---|---|
| `id` | 稳定标识：`{项目名}/{相对目录}/{规则}` |
| `label` | 显示名，默认取自规则（如"后端服务"、"开发服务器"），可改 |
| `kind` | 五种之一，见 §1.3 |
| `command` | 命令行参数列表（`static` 型为空） |
| `cwd` | 工作目录（相对项目根） |
| `port` / `url` | 预期端口与浏览器地址（可空） |
| `confidence` | `high` / `mid` / `low`，低置信在界面标 ❓ 提醒确认 |
| `rule` | 命中的规则号（R1~R12），界面可追溯"为什么这么启动" |
| `locked` | 用户覆盖后置 true，重扫不冲掉 |

### 1.3 启动项的五种类型（kind）

| kind | 含义 | 进程归属 | 例子 |
|---|---|---|---|
| `service` | 外部进程起的持续服务，有端口 | 外部进程 | `node serve.js`、`mvn spring-boot:run` |
| `app` | 桌面应用进程，无端口 | 外部进程 | `java -jar xx.jar`、`.pyw`、Godot 成品 exe |
| `static` | 纯静态页，file:// 直开 | **无进程** | Book_MoonEssays 的 index.html |
| `embedded` | 由**精灵自身**起 http 服务来托管 | 精灵内置线程 | PWA 项目（需要 http 环境） |
| `script` | 跑完即退的一次性脚本 | 外部进程（短命） | `模糊文档内容.bat` |

### 1.4 启动组（Launch Group）

当项目根目录下命中多个子目录启动项（如 `backend/` + `frontend/`），精灵将它们组成一个**启动组**：界面上显示【一键启动全部】和【全部停止】，并可定义顺序与间隔（默认先起后端、等 5 秒再起前端）。P_ 系列 4 个项目是典型。

## 2. 扫描范围与深度

- 扫描根：`profiles.json` 的 `scan_roots`（默认 `F:\Workspace\Space_Zcode`），可配多个。
- 每个扫描根下取**一级子目录**为项目根（`.rar` 文件、隐藏目录、`node_modules` 等直接忽略）。
- **下钻白名单**：项目根下仅递归进入这些约定子目录找启动标记（最多再下钻 2 层）：
  `frontend/ backend/ h5-app/ server/ client/ web/ editor/ app/ sites/`
  ——这覆盖了盘点中全部真实情况（`frontend/package.json`、`server/offline-sync/pom.xml`、`sites/interactive/` 等），又不会把 `tools/`、`docs/`、`data/` 这类素材目录误当子项目。
- 扫描结果缓存（目录 mtime），未变化的目录跳过重检（见 docs/05）。

## 3. 规则表（按优先级从高到低）

同一目录内，编号小者优先；不同规则可在同一项目的不同目录分别命中。

### R1 · 启动脚本（bat / cmd / ps1）——最高优先
- **标记**：目录内 `*.bat` / `*.cmd` / `*.ps1`（**中文文件名同样识别**，如 `启动ComfyUI工具.bat`）。
- **判定**：文件名含"启动/start/run/launch/serve"或内容里出现 `python`/`node`/`mvn`/`npm`/`powershell` 等解释器调用 → 视为启动脚本；明显是构建/安装用途的（文件名含 `build`/`install`/`upload`，如 `build_windows.bat`）**排除**。
- **动作**：`kind` 按脚本内容判断（有端口线索 → `service`，否则 `script`），**直接执行该脚本，不绕过它自己拼命令**——项目入口的既有逻辑（如 ComfyUITool 的端口顺延）原样生效。
- **端口提取**：正则扫脚本内容 `set PORT=(\d+)`、`--port (\d+)`、`http.server (\d+)`、`:(\d{4,5})`。
- **置信**：high（用户亲手写的入口，最强信号）。

### R2 · 嵌入式运行时
- **标记**：`runtime/python.exe`（项目自带 Python，如 Tool_NodeCanvas）。
- **动作**：该项目的 Python 类启动一律优先用自带运行时，**不调用系统 Python**。
- **说明**：R2 通常与 R1 同时存在（bat 里已经写了 runtime 路径），此时 R1 执行 bat 即可，R2 只作为知识记录，供"编辑启动方式"时默认填入。

### R3 · package.json（Node / Vite）
- **标记**：目录内有 `package.json`。
- **命令选择**：`scripts` 里按 `dev` > `start` > `server` 取第一条；Windows 下实际执行 `npm.cmd run <script>`。
- **端口提取**：① scripts 内联 `--port (\d+)`；② 同目录 `vite.config.js` 的 `server.port` 或 `proxy.target`；③ 都没有 → 用框架默认（Vite 5173）并从**日志回读**实际端口。
- **kind**：`service`（dev/start）或 `app`（electron 之类，暂未出现）。
- **前置检查**：`node_modules/` 不存在时启动前提示"依赖未安装"（v0 只提示，不代跑 `npm install`）。

### R4 · pom.xml（Spring Boot / Maven；v0.4 加插件门槛）

> **v0.4 起仅当 pom 声明 `spring-boot-maven-plugin` 才生成启动项**：多模块工程的聚合根（packaging=pom）与纯库模块（ModularSuite 的 common/framework/system 等）被抑制——对它们跑 `spring-boot:run` 要么报错要么无意义（校准：ModularSuite 8 模块仅 admin 带插件，端口 8014）。标签：单后端项目叫「后端服务」；多模块并存时「后端服务（模块名）」。
- **标记**：目录内有 `pom.xml`。
- **命令**：`mvn spring-boot:run`（在 pom 所在目录执行；编译型项目再议）。
- **2026-09-22 实现注记**：项目根有 `.tools/maven/bin/mvn.cmd`（P_ 系列自带 Maven 3.9.9）时**优先用自带 Maven**，与各项目运行手册一致——PATH 上不同版本 Maven（如 3.6.3）的 resolver 对 `~/.m2` 缓存元数据不完全互认，换版本会触发重复下载与行为差异。无 `.tools` 的（P_MobileLabNotes）仍用 PATH 的 `mvn`。
- **端口提取**：读 `src/main/resources/application.yml`（或 `.properties`）的 `server.port`，取不到用 8080。
- **kind**：`service`；**前置探测**：`mvn`、`java` 在 PATH 上（v1 实现，超时 2 秒按缺失处理）。

### R5 · 游戏引擎 / .NET
- **R5a Godot**：标记 `project.godot`（常伴 `.csproj`）。动作：优先找 `build/windows/*.exe` 成品直接运行（`kind=app`）；没有成品则给 `dotnet build` 的 script 项 + 提示用 Godot 编辑器打开。
- **R5b 纯 .NET**：`.sln`/`.csproj` 而无 godot 标记 → script 项 `dotnet build`（当前工作区未出现，规则预留）。

### R6 · 单 jar
- **标记**：目录里唯一/主要文件是 `*.jar`（如 Tool_PromptKit）。
- **动作**：`java -jar <文件名>`，`kind=app`；前置探测 `java`（需 JRE）。

### R7 · .pyw（无控制台 Python GUI）
- **标记**：`*.pyw`（如 Tool_ProcessPortManger）。
- **动作**：`pythonw <文件>`（优先）或 `python <文件>`，`kind=app`，不捕获控制台。

### R8 · Node 服务脚本（无 package.json）
- **标记**：根目录或 `tools/`、`server/`、`app/` 下存在 `serve.js` / `server.js` / `app.js` / `main.js`，且**无** package.json（有则归 R3）。
- **动作**：`node <脚本> [端口]`，`kind=service`。
- **端口提取**：① 正则扫脚本源码（`listen(8787`、`PORT = 8787`、`--port` 默认值）；② 提不到就不传端口，**启动后从日志回读**（正则 `http://(127\.0\.0\.1|localhost):(\d+)`），回读成功再开浏览器。
- **注意**：R8 **优先于 R9**——G_MythicJourney 两个项目同时有 `index.html` 和 `serve.js`，但 nodecanvas-lab 页面依赖服务端，必须起 serve.js 而非 file://。

### R9 · index.html（静态页分级）
- **标记**：目录内有 `index.html`，且未命中更高规则。
- **R9a PWA**：同目录同时有 `manifest.json` + `sw.js` → 必须 http 环境 → `kind=embedded`：**由精灵自身起一个 http.server 线程托管该目录**（绑定 127.0.0.1，免防火墙弹窗），端口用档案里记录值或自动选空闲口并记住。
- **R9b 纯静态**：其余情况 → `kind=static`，`file:///` 直开，零进程。
- **集合型**：一个项目下有多个含 index.html 的子目录（如 Tool_MiniGen 的 7 个小作品、Book_RiverNotes 的 sites/）→ 每个子目录一个 static 项，项目标记"集合型"，界面折叠展示。

### R10 · Python 脚本型
- **标记**：`requirements.txt` 或根目录 `*.py`，未命中以上规则（如 G_NovaPlayer、Tool_TableCaption、Tool_DataAudit）。
- **动作**：识别入口（`main.py` / `__main__` 包 / README 里的运行命令），给出 `script` 或 `app` 项；需要位置参数的（Tool_TableCaption 要传 docx 路径）标记"需参数"，启动时弹输入框。
- **置信**：mid~low（入口猜测成分大，界面标 ❓）。

### R11 · 文档型
- **标记**：以上全部未命中，目录里只有 md/docx/pdf 等。
- **动作**：不生成启动项，列表中灰显为"文档"；右键"打开目录"。
- **置信**：high（纯文档没有可启动的东西，这个判断不会错）。

### R12 · 打包成品（dist/ 内的 exe；v0.4.3）

> 2026-09-23 需求：PyInstaller/.NET 打包后的执行文件也是合法启动方式，应显示在详情里。实现在 `detector._r12_packaged_exe`。

- **标记**：项目根下 `dist/` 目录**一层之内**的 `*.exe`（只看这一层，`dist/sub/` 深层不递归）。
- **为何只认 dist/**：2026-09-23 全工作区校准——打包产物全部位于 `dist/`（Tool_FileDiskUsage 的 PyInstaller 单文件、Tool_NetworkTrafficUsage 的 .NET 框架依赖发布、Tool_ProcessPortManger、本项目自身）；`build/windows/` 是 R5a Godot 的专属约定，天然错开不重复；项目根直接放 exe 当前无真实命中，宁缺毋滥。
- **排除**：① 文件名词干为 `createdump`（.NET 发布自带的崩溃转储工具，Tool_NetworkTrafficUsage/dist 实测噪音）；② 文件名含 `setup`/`install`/`unins`/`update`/`upgrade`/`安装`（安装器特征，惯例防误报）；③ 每目录最多 3 个（防失控）。
- **动作**：`kind=app`、`console=False`、cwd=exe 所在目录、`command=[文件名]`；label 取 exe 基名；置信 high（位置与形态的确定性高）。
- **地位（与主规则不同）**：R12 是**附加项**——不占"每目录最多一条主规则"的名额，也不参与"项目命中服务项后抑制静态页"的逻辑。源码启动方式与打包产物并存是常态（本项目即 R10 源码 + R12 dist 成品两项并列），用户按需选择。缓存 fmt=4 起生效。
- **启动行为**：app 型统一 `CREATE_NO_WINDOW` + 输出捕获（v0.4.3，见 docs/03 spawn 表）——打包 exe 崩溃时的报错（stderr）进精灵运行日志，不再"一闪而过"。

## 5. 人工覆盖机制（检测只是建议）

1. 用户在"编辑启动方式"里改过任何字段 → 该启动项 `locked=true`，写入 `profiles.json`。
2. 重扫时：`locked` 项原样保留；未锁项被新检测结果**替换**（项目结构变了就跟着变）。
3. 用户可手工**新增**启动项（如给文档型项目挂一个"用 Typora 打开索引"命令）、**禁用**某启动项（保留定义但列表隐藏）。
4. "恢复自动检测"按钮：清掉某项目的全部覆盖，回到检测值。

## 7. 已知局限与兜底

| 局限 | 兜底策略 |
|---|---|
| bat 内容解析不出端口/类型 | 整段执行 bat 不受影响；端口靠日志回读补 |

### 8.5 分组与身份键（v0.4.4）

> 2026-09-23 需求：未手工分组的项目默认按**父文件夹名**分组；同时把"跨扫描根同名项目"的身份键问题一并定约。实现：`core/profiles.py::effective_group`（纯函数）+ `core/scanner.py::assign_keys`。

**嵌套不冲突的前提（既有模型重申）**：扫描只取各扫描根的**一级子目录**为项目实体（§2），子文件夹里的项目标记不产生第二个实体，只被吸收为父项目的启动项（cwd 区分，跨扫描单元互不抑制——即 §1.4 启动组形态）。因此"父文件夹既有子层级项目、本身又有项目信息"的结果是**一个项目、多张启动卡**（父根 `cwd=""` 与子目录项平级共存），不存在"父既是组头又是项目"的双重身份。

**分组三档**（优先级从高到低，`effective_group`）：

1. **手工分组**：profiles.json 里 `group` 非空且非 `"-"` → 用它（沿用 §8.3"用户标注永远优先"原则）；
2. **自动父文件夹**：`group` 为空 → 取 `basename(父目录)`，**仅当父目录是某个扫描根**（当前模型下等价于"按扫描根分组"，多根场景才有意义）；custom_projects 的父目录不是扫描根，不自动分组；`Nginx_` 合成站点走下面的 nginx 组（v0.4.5）；
3. **退化平铺**：待自动分组的项目全部来自**同一个**父文件夹时（单扫描根即如此），不显示组头、按未分组平铺——保证单根工作区观感与旧版完全一致。

- **哨兵 `"-"`**：profiles 里 `group="-"` 表示显式不分组（属性对话框下拉提供），解决"自动分组无法退出"的问题；`"-"` 是保留值，不能当真实组名。
- **nginx 站点默认分组（v0.4.5）**：仅 nginx 引用的合成站点（`Nginx_` 前缀，§9.3 N3）的自动分组名按**来源 nginx** 取（`ngxscan.site_group` 纯函数）：本机只发现一份在用配置 → 统一 `nginx`；多份 → `nginx(来源 conf 路径)`（conf 缺失时 `nginx(?)`）。nginx 组**不参与**普通项目的退化折叠判定——单根工作区里站点归入 nginx 组头、其余项目照旧平铺。三档优先级对站点同样成立：手工分组 ＞ `"-"` ＞ 自动 nginx 组。
- 拖拽到自动组头 = 把该组名写成手工分组（固定）；详情页组名标签显示**生效分组**。

**身份键（key）**：跨扫描根出现同名项目时，按 `scan_roots` 顺序**首个保留裸项目名**，后续项升级为「根名/项目名」。key 用于 scan_cache.json 字典键、profiles.json 项目档案、GUI 选中/排序/拖拽、日志文件名（`safe_project_name` 把 `/` 清洗为 `_`）。无重名时 key == 项目名 → **旧 profiles.json / scan_cache.json 完全兼容，零迁移**。

- 启动项 id（= 进程注册表 rid）首段同步随 key 改写（`detector.rekey_entries`），保证 rid 全局唯一、同名项目的进程互不顶替。
- **已知限制**：① 端口知识库仍按裸项目名读写（重名项目共享一条，detector 与学习回调同口径）；② 首个同名项目被移走后，后续项会接管裸名键并继承其档案；③ 两个扫描根本身同名时「根名/项目名」仍可能撞键（极端场景，暂不处理）。

## 9. nginx 关联检测（v0.4.2：N 系规则）

> 2026-09-22 需求：有些前端不走 dev server，而是由 nginx 托管静态目录（本机两种形态：Windows 裸装 nginx 与挂进 Docker Desktop 的 nginx）。扫描时读取系统 nginx 配置，把 server 块与工作区项目关联起来，并列出"只在 nginx 里出现"的站点。实现在 `core/ngxscan.py`（纯函数），N 系规则**不生成进程型启动项**——nginx 进程由用户自己的方式管理（docker/裸装服务），精灵只提供访问地址与关联信息。

### 9.1 配置发现（find_nginx_confs，可多份）

按可信度顺序收集**全部**候选，逐份解析、各自关联后合并（每条关联记着自己的来源配置文件）：

1. `settings.nginx_conf` 手动指定（文件或目录；v0.4.7 起**可多个，每行一个**，设置框多行 + 浏览可多选，有效份全部解析；部分无效则忽略无效份并在扫描日志列明，**全部无效不回落自动探测**，界面提示）；
2. 运行中的 nginx 进程（psutil，取 exe 旁 conf/nginx.conf）；
3. PATH 上的 nginx；
4. 各盘常见安装目录：`{盘}:\nginx\conf\`、`{盘}:\tools|software\nginx\conf\`、`{盘}:\Program Files\nginx*\conf\`；
5. **盘根独立 nginx.conf**（本机真实形态：`F:\nginx.conf` 是挂进 Docker 的那份）。

过滤：路径含备份特征（`- 副本`、`-copy`、`-backup`、`备份`、`.bak` 等）的自动候选跳过——2026-09-22 实测 `D:\Program Files\nginx - 副本\` 是旧版配置，纳入只会产生重复站点。上限 6 份 / 100 个 server 块。

### 9.2 解析（自研轻量解析器，无第三方依赖）

- 词法：`#` 注释、引号串（alias "F:/… front/" 这类带空格路径）、`;` `{` `}`；按指令树递归收集 `server` / `upstream` / `include`（glob 支持，相对主配置所在目录，缺文件静默跳过）。
- server 提取：`listen`（含 `127.0.0.1:8080`、`[::]:80`、`80 ssl` 形态）、`server_name`、每个 `location` 的 `root` / `alias` / `proxy_pass`（含 `=`、`~`、`^~` 修饰符）；location 可嵌套，内层并入外层统计；server 级 root 折算成 `location /`。
- `upstream`：`proxy_pass http://upstream名` 经 upstream 解析到真实 host:port。
- root/alias 路径解析：Windows 绝对路径原样；`/mnt/<盘>/…` 按 WSL 挂载转 `<盘>:\…`；其余 Linux 绝对路径（`/opt/…`、`/mnt/software/…`）视为**容器/外部路径**（本机不存在，展示原样）；相对路径锚定 nginx prefix；含 `$变量` 跳过。

### 9.3 关联规则

| 规则 | 判定 | 产出 |
|---|---|---|
| **N1 路径关联** | location 的 root/alias 解析出的 Windows 路径落在某项目目录（含子目录如 `Web/`、`dist/`；嵌套时**最深项目胜出**） | 项目获得"nginx 托管前端"信息：访问地址（listen + location 前缀）、端口、root（含"项目内相对位置"）、来源配置；该 server 的反代后端也附在这里 |
| **N2 端口关联** | proxy_pass（含经 upstream）指向 `localhost:PORT`，且 PORT 是某项目启动项端口或端口知识库端口 | **双向**：前端侧（N1/N3 条目里）列"反代后端 PORT → 项目名"；后端项目标"被 nginx :前端口 /loc/ 反代"。只按端口命中，属**可能关联**，界面如此措辞 |
| **N3 仅 nginx 站点** | server 有静态 root 但不落在任何项目 | 合成项目 `Nginx_<目录名>`（目录名跳过 dist/ui/web 等无信息量段）：类型 `Nginx`、static 启动项 = 打开 `http://localhost:<listen>/`，端口列显示 listen；root 为本机路径时可"打开目录"，容器路径则标注"本机不存在" |

- URL 一律 `http://localhost:{listen}{location}/`；`=` 精确与 `~` 正则 location 不产 URL（但仍参与 root/代理统计）。
- 站点/关联每次扫描**全量重算**（解析是毫秒级），不走项目 mtime 缓存；关掉 `scan_nginx` 开关即清空全部关联与站点。
- 精灵**不管理 nginx 进程**（不启动/不停止）——站点的"启动"按钮 = 打开访问地址（static 型语义）。

### 9.5 nginx 分组引用行（v0.4.8）

**动机**：N1/N2 关联写进真实项目后，在用的 nginx 配置在列表里**零可见**——本机 D 盘裸装 nginx（9003 托管 harbor、18080 托管 web-office-suite）不像 F 盘容器路径那份产出 N3 合成站点，用户只看得到 F 盘组，误以为"正在运行的那份没被识别"（2026-10-01 需求轮）。

**设计**：

- `ngxscan.group_refs(drs)` 纯函数（GUI 与 selftest 共用）：从全部 DetectResult 的 dr.nginx 取 role=host/proxy 的关联，按（来源配置 conf, 目标项目 key）合并——同一项目在同一配置下的 N1+N2 归并成一行，roles 去重保序、ports 升序去重、urls 保序去重；**role=site 不进引用行**（合成站点本身已是独立条目）。返回 `{conf: [{key, name, roles, ports, urls}, ...]}`，组内按名称排序。
- 展示：nginx 组内项目行之后插入引用行，name 列 `　↗ {身份键}`，type 列 `已关联 · 托管/反代`，状态点与前景色沿用**目标项目当前状态**（与跳过去看到的一致）；组头计数 = 项目行 + 引用行。只有引用行没有站点的配置（D 盘情形）照常建组——正在运行的 nginx 由此获得可见的组。
- 分组名复用 `site_group(conf, 全部来源 conf 集合)`，与合成站点同规则：多份在用配置时按来源带路径命名（`nginx(F:\nginx.conf)`），单份统一 `nginx`。
- 行 iid 前缀 `r::<conf>|<key>`，**不进 `_row_project`**（不可启动、不可拖动排序）。交互：**双击 = 跳转**定位目标项目行并打开详情（目标行被搜索过滤隐藏时先清搜索词）；**右键 = 打开访问地址**（多条逐列，`_visit`）/ 跳转到项目 / 打开配置文件（`_start_file`）。
- 开关：引用行受 `scan_nginx` 总开关控制（关联清空自然消失）；`nginx_show_only` 语义不变（只关 N3 站点合成）。v0.4.16 起**仅按端口推测的引用行默认不显示**（`settings.nginx_show_possible`，默认 false）：`group_refs(drs, include_possible=False)` 滤掉 roles 只有 proxy 的行（同端口撞车的项目拷贝产出大量"并无真实关联"条目，如三份 Q7 拷贝都声明 28080 被 F:/D 两份 conf 命中），host+proxy 混合照留（有真实托管，proxy 只是附加信息），滤空的配置整组不出现（该 conf 若有 N3 站点则组仍在）。设置对话框 nginx 区勾选开关。
- 散落/未使用配置的**排除机制**：2026-10-01 决策不自动判定"没有程序在用"（Docker 挂载的配置在 Windows 进程表完全不可见，会误杀 F:\nginx.conf 这类真实在用的），改为手动排除清单，见 §9.6（v0.4.9）。
- selftest：`check_nginx_refs` 纯函数不变量（同 conf 同项目合并/ports·urls 去重、site 不进引用行、conf 分组、组内按名称排序、空输入/纯 site/键缺省回落）。

### 9.6 nginx 配置排除机制（v0.4.9）

**动机**：散落的 nginx.conf（盘根孤儿配置、已卸载残留）会被 §9.1 的惯例探测捞出来，产出无关站点/分组。自动判定"在用"不可靠（Docker 挂载配置进程表不可见），故做**确定性手动排除**。

**设计**：

- profiles `settings.nginx_excluded`：多行文本，每行一个路径（与 `nginx_conf` 同风格；容忍首尾引号与空白行，去重保序；**不校验存在性**——指向已删除文件的条目也可保留）。
- `ngxscan.filter_excluded(confs, excluded_text) -> (保留, 排除)` 纯函数：按 normcase 归一后的**整路径精确比对**（Windows 大小写/分隔符不敏感，不做目录前缀匹配），两个输出各自保持原顺序。
- 接入点在 `apply`：候选取定后、解析前过滤——`find_nginx_confs` 保持返回全量（供设置对话框勾选 UI 使用）。**手动指定的配置同样受排除约束**（同一路径既指定又排除 = 排除赢，防自相矛盾）；过滤在 `[:MAX_CONFS]` 截断之前，被排除的不占名额。
- 扫描日志注明：部分排除时输出"已排除（设置里勾选，不参与关联）：{路径}"；全部被排除时报"找到的 N 份 nginx 配置已全部在设置里排除"。被排除的配置不产生任何关联/站点/分组（`_nginx_confs` 收集不到它，分组命名随之回落——只剩一份时组名从 `nginx(路径)` 退回 `nginx`）。
- GUI：设置对话框 nginx 区新增"排除的 nginx 配置（每行一个）"多行框 + 「勾选要排除的配置…」——弹窗列出探测到的全部候选与当前已填排除项（normcase 去重合并，勾选 = 排除），确定写回文本框；候选口径与 apply 一致（手动指定模式下只列手动那几份）。
- **顺修两处 v0.4.7 回归**（2026-10-01 端到端冒烟发现）：① `apply` 头部曾被改为无条件 `manual_split(manual)`，手动框留空时自动探测（`find_nginx_confs`）整条丢失、nginx 关联恒为空——现恢复"留空 = 自动探测，非空 = 只认清单"；② "部分手动路径无效"的提示行被 `lines` 重置吞掉、正常路径永不显示——现与排除注记一并并入 `notes` 置于各配置行之后。
- selftest：`check_nginx_excluded` 纯函数不变量（normcase 匹配/保序/引号空白容忍/全排除/空文本/不误伤/重复行只排一次）；另有 apply 级端到端冒烟（真实两份配置 × 排除/全排除/不排除/指定+排除四场景）。

## 10. Docker 容器关联与启停（v0.4.15：D 系规则）

> 2026-10-01 需求轮：容器（尤其容器里跑的 nginx）与工作区项目互相看不见——F:\nginx.conf 这类挂进 Docker 的配置在 Windows 进程表完全不可见，精灵此前只能按文件位置猜"在用"。实现在 `core/dockman.py`（仿 fwman：纯函数与 I/O 分离，读 = docker ps/inspect 输出 JSON，写 = docker start/stop）。**管理边界（收窄 v0.4.2 的前例）**：nginx 进程仍不管理，但**关联到的容器**可以启停（右键/详情页，停止弹确认）；从未关联的容器精灵绝不碰。所有容器状态均为"扫描时"快照。

### 10.1 关联规则（D 系）

| 规则 | 判定 | 产出 |
|---|---|---|
| **D1 配置挂载** | 某 nginx.conf（或其所在目录）被容器 bind mount | 该配置获得"在用"凭据：详情页 nginx 区 conf 行标注「容器 oo（运行中 · 扫描时）」；引擎在跑且扫描时无任何容器挂载它 → 标注「扫描时未发现挂载它的容器（可能未在用）」 |
| **D2 端口发布** | 容器发布宿主端口 P（`docker -p`），P 与某项目启动项端口一致 | 项目详情页「端口 P 与容器 X 的发布端口相同——可能关联（状态）」；外部运行感知（docs/04 §2）的监听备注升级为「端口 P 由 Docker 容器 X 发布」且**永不给结束进程**（监听者是 docker backend，杀它只断端口发布不碰容器）。匹配一律用**宿主端口**（宿主端口 ≠ 容器内端口） |
| **D3 目录挂载** | 容器 bind mount 的宿主源路径落在某项目目录内 | 项目详情页「项目目录挂载进容器 X（状态）（项目内 dist/）」——确证级关联，嵌套项目最深胜出 |

- 挂载源归一（`normalize_mount_src` 纯函数）认四种形态：`F:\x`、`F:/x`、`/host_mnt/f/x` 与 `/run/desktop/vm/hostd/f/x`（Docker Desktop 内部视角）、`/mnt/f/x`（WSL）；命名卷与其余 Linux 绝对路径与宿主无关，不参与匹配。
- 数据写进 `DetectResult.docker`（`{kind: mount|port, container, image, state, host_port?/rel?}`）与缓存 `detected.docker`；合成站点的 site dict 注入 `container`/`container_state`（D1）；扫描快照存缓存 `@docker`（engine/containers/conf_containers/published），自动扫描关闭时随之恢复。
- 引擎状态三态：`off`（CLI 缺失）/ `down`（引擎不可达）/ `up`。scan_docker 关 → 清空关联；引擎 off/down → **不写不删**（保留上次结果），扫描日志记一行，界面右键提供「启动 Docker Desktop」（拉起后后台轮询 ≤90 秒，就绪自动重扫）。

### 10.2 容器启停（只动关联到的）

- 入口：项目行/站点行/引用行右键「启动容器 · X」「停止容器 · X」，详情页 Docker 区每行一个上下文按钮（运行中→停止容器，否则→启动容器）。
- 与精灵「停止」的区别：容器是 Docker daemon 的系统状态——停止弹确认（其中服务会不可达），启动不弹；`docker start/stop` 在后台线程执行（CLI 全程 CREATE_NO_WINDOW + 超时），完成回写内存与缓存状态快照并刷新，免整轮重扫。
- 引擎级失败（操作时引擎已停）转化为「现在启动 Docker Desktop 吗？」；找不到启动器时提示手动启动（候选：`%ProgramFiles%\Docker\Docker\Docker Desktop.exe` 等）。
- 上限兜底：容器 ≤50 份、逐个 inspect 挂载 ≤10 份（nginx 镜像/名字或发布端口命中项目端口∪端口知识库∪conf listen 的优先；总数 ≤10 时全量 inspect）。
